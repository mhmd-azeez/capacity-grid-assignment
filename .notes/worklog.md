## 2026-09-27

- Working on `feat/capacity-view`. `origin` is my fork, toggl's repo is `upstream`.
- Most assignment rows in the seed are exact duplicates, each one repeated 14 times. Adding them up as-is would inflate everyone's hours, so we'll probably need to dedupe. Not decided yet.
- `hours_per_day` only has values like 0.125 and 0.5, which look more like fractions of a day than hours. Not sure yet how to read it.
- Lots of assignments run into the weekend, so whether weekends count is going to matter. Eli Nakamura has 0 weekly hours but still has work assigned, so there's no sensible percentage for him.
- Scratch the dedupe idea. The duplicates come in pairs: each assignment is 14 rows at some value plus one more row at double that value, so the rows add up to 16 times the base. Added up as-is, you get whole hours per day and week totals that look like a real team. Deduping would make everything wrong. That also settles `hours_per_day`: once all the rows are added up, it's plain hours.
- The first version of the capacity endpoint takes the data completely literally, weekends included. I wanted to see what the raw data says before correcting anything. Ana's first week comes out at 56 of her 40 hours.
- The endpoint always works in whole weeks, Monday to Sunday, even if you ask for a Wednesday. That way a column always means a full week. More than two years at once gets a 400.
- Dates are kept as plain dates everywhere, never timestamps. Postgres quietly turns some date functions into timestamps with a time zone, and when I set the session to UTC+14, Monday Dec 29 came back as Sunday. Browsers west of UTC have the same problem with timestamps in JSON, so the API sends "2025-12-29" style strings.
- The response lists the weeks once, then one row per person with their weekly hours and an array of allocated hours, one per week. Capacity only exists per person in the database, so that's where it lives in the response too. It also means saving a person's new hours only changes one number on the client.
- Looked at the output across all the data. A third of busy weeks come out over capacity, and most of that is weekends: every assignment starts on a Monday, but plenty run to Saturday or Sunday. Counting only weekdays cuts the over-allocated weeks from 4,779 to 1,626.
- We're counting all 7 days for now and will come back to it. That's why Ana still shows 56 of 40.
- The generated data runs in a three-week cycle, busy, less busy, then empty. The week of Jan 12, 2026 is the exception. It only has the handful of hand-written assignments for Ana, Bo, Cem and Dee, and the default date range is set to show exactly those. Holidays like Jan 1 count as normal days because there's no holiday data.
- The grid's first version is a plain table. If the range changes while a request is still loading, the old request gets cancelled so it can't overwrite the new one.
- Names don't sort alphabetically: "Guillermo Álvarez" ends up after "Guillermo Ruiz", and the Greek, Arabic and other non-Latin names all end up at the bottom. The Alpine Postgres image sorts text byte by byte. Asking for ICU sorting in the query fixes it, but I haven't changed it yet.
- The heading says the range ends on Jan 16, a Friday, but the grid actually runs to Sunday the 18th. I'll fix it with the navigation work.
- Only over-allocated weeks get highlighted, in red with the extra hours next to them. Eli has 0 hours of capacity, so any work at all shows as over. I skipped anything fancier because the brief just says over-allocation should be obvious at a glance.
- Dates on the frontend go through Temporal's `PlainDate`, which is a date with no time or zone attached, so the day-shifting problem can't happen. I'd hand-written the helpers at first but switched, since the library does exactly this.
- The range lives in the URL, so a refresh or a shared link opens the same weeks. It replaces the history entry instead of adding one, so the back button doesn't step through every week you clicked past.
- While a new range loads, the old grid stays on screen, faded, instead of going blank on every click. If the load fails, the old grid goes away and you get the error with a retry button, because leaving it up would show numbers for different weeks under the new heading.
- A bad range in the date inputs (end before start, or over two years) shows a message and never reaches the API.
- Saving someone's weekly hours returns the updated person and nothing else. Their allocations don't depend on capacity, so the grid only needs that one number back.
- Weekly hours can be anything from 0 to 168, the number of hours in a week. 0 has to be allowed because Eli is already at 0.
- There's no history of capacity in the schema, so a change applies to every week, past ones included. If someone drops from 40 to 32 hours next month, the grid will also show them at 32 last year. Proper fix is capacity with an effective date, which is out of scope here.
- Two managers saving the same person at once: last write wins. No conflict check.
- Deferred: simultaneous edits and capacity history. The first could be fixed by sending the value the manager started from and refusing the save with a 409 if it has changed since. The second needs a table of capacity changes with effective dates, which means changing the schema.
- Editing uses a modal that waits for the server, then updates that one person's row from the response. We went back and forth on optimistic inline editing, which is faster when you're changing lots of people, but it needs rollback, a way to show unsaved changes, and handling for saves racing each other. Deferred for now. There's no full reload after a save because nothing else on the grid depends on someone's weekly hours.
- If a save fails, the dialog stays open with what the manager typed and says the change wasn't saved. The grid keeps the last saved value, so it never shows a number the server doesn't have. Escape can't close the dialog while a save is in progress.
- If the grid was loading new weeks when a save finished, it loads them again, because that response might have been fetched before the save and carry the old hours.
- Tested a real failure by stopping the API container mid-session. The Vite proxy turns that into a 502, so the manager sees "the server had a problem" and not "couldn't reach the server". Both say the change wasn't saved, so I left it.
- Names now sort properly. The query asks Postgres for ICU sorting, because the default on this Alpine image sorts byte by byte and put "Álvarez" after "Ruiz". Paging needed a sort order that doesn't move, so this had to be fixed first.
- The grid pages through people, 20 at a time, with the page number in the URL so a link opens the same page. The query picks the page of people first and only works out allocations for them.
- I first built cursor paging, which doesn't shift when people are added mid-browse. We switched to plain page numbers because a cursor in the URL needs backwards paging and a position count before links work. With a roster that rarely changes during a session, the odd shifted row is fine. Paging by the last person's id (`?after=123`) would be the better long-term option.
- The "People 41–60 of 500" label follows the rows on screen, not the page just clicked, since the old rows stay visible while the next page loads. A link past the last page lands on the last page.
- Left alone: a page covering two years takes about 0.2s, because Postgres scans the whole assignments index to find the 20 people on the page instead of looking each one up. Three weeks is well under 0.1s.
- Switched to counting Monday to Friday only. The hand-written rows made the case. With weekends counted, Ana and Bo look over-allocated only because of Saturday and Sunday, while Dee is over because of a real double-booking and Eli because he has no capacity. With weekdays only, only Dee and Eli are red. A note under the dates says weekends aren't counted. Not handled: people who genuinely work weekends, per-person working days, and holidays.
- Added a name filter. It runs on the server, since the grid only has one page at a time. It matches anywhere in the name, ignores case, and treats %, _ and \ as plain characters. A new search starts from page 1 and goes in the URL. Accents have to match, so "soren" won't find "Søren". Fixing that needs the unaccent extension or a custom collation, both schema changes.
- The filter is a plain scan of the people table, about 0.2ms for 500 people. If the roster ever got into the hundreds of thousands, a trigram index (pg_trgm) would speed it up. That's also why it uses ILIKE: I first wrote it with strpos, which that index can't help.
- Possible follow-up for search: normalise names before matching. For Latin names that means stripping accents, so "soren" finds "Søren" and "alvarez" finds "Álvarez". Arabic names need the same kind of thing: treat the alef forms (أ إ آ) as plain ا, ignore diacritics (tashkeel) and the tatweel stretch character, and probably treat ة and ه, and ى and ي, as the same letter. Either way it means normalising both the stored name and the search the same way, most likely in a generated column or with unaccent, which is a schema change.
- Fixed the slow two-year query from earlier. Most assignments are 15 rows with the same person and dates, and we were splitting every one of them into days before adding up. Now rows that share person and dates get added up first, then split. A two-year page went from about 200ms to about 20ms, and the output is identical for all 500 people across 83 weeks (compared before and after).
- Replaced the edit modal with editing in the row itself: the hours cell turns into an input with Save and Cancel, and Enter and Escape work too. It still waits for the server. While a row is being edited, the week buttons, dates, search, paging and other rows are locked, so an unsaved or failed change can't disappear off screen. Saving when the field loses focus, without buttons, would feel lighter. Left for later, because it raises questions about what happens to an invalid or failed value when focus moves on.
